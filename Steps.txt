2. STEP 1: MODELING FIXED STATES WITH ENUMERATIONS (ENUMS)
================================================================================

Files Created:
  - AccountStatus.java
  - BookStatus.java

--------------------------------------------------------------------------------
A. WHAT HAS BEEN DONE
--------------------------------------------------------------------------------
We created two Java Enumerations (`enum`):
1. `AccountStatus` to represent the status of a library user's membership.
2. `BookStatus` to represent the availability of a physical book in the library.

--------------------------------------------------------------------------------
B. THE CODE
--------------------------------------------------------------------------------

File: src/AccountStatus.java
---------------------------
public enum AccountStatus {
    ACTIVE, 
    CLOSED
}

File: src/BookStatus.java
------------------------
public enum BookStatus {
    AVAILABLE, BORROWED;
}

--------------------------------------------------------------------------------
C. CODE EXPLANATION
--------------------------------------------------------------------------------
- `public enum AccountStatus`: The `enum` keyword tells the Java compiler that
  this is a special class whose instances are limited to a fixed set of constants.
- `ACTIVE, CLOSED`: The allowed constant values. By Java naming convention, enum
  constants are written in all UPPERCASE characters.
- In `BookStatus.java`, `AVAILABLE, BORROWED;`: The semicolon `;` at the end is
  optional in Java if there are no additional fields or methods following the
  constants, but it is valid and standard practice.

--------------------------------------------------------------------------------
D. CORE CONCEPTS USED
--------------------------------------------------------------------------------
1. Enumeration (`enum`): A specialized Java type used to define collections of
   constants. Under the hood, Java creates a class extending `java.lang.Enum`.
2. Type Safety: The compiler guarantees that a variable of type `BookStatus` can
   ONLY hold `BookStatus.AVAILABLE` or `BookStatus.BORROWED` (or null). It cannot
   hold invalid strings like "lent", "missing", or "checked-out".
3. Elimination of "Magic Strings": In beginner code, status is often stored as a
   plain String: `String status = "available";`. If someone accidentally types
   `"availible"` (a typo), the code compiles fine, but checks like
   `if (status.equals("available"))` will fail silently at runtime, causing bugs.
   With enums, the compiler flags any spelling mistake immediately.

--------------------------------------------------------------------------------
E. WHY WE DID THIS STEP
--------------------------------------------------------------------------------
Before writing classes that represent people or books, we must establish the
operational rules of our universe. A book cannot be in an arbitrary state; it has
specific rules (e.g., you cannot borrow a book that is already BORROWED). By
defining enums first, we provide a type-safe contract that the rest of the system
can safely rely upon.

3. STEP 2: CREATING THE BASE IDENTITY ENTITY (PERSON)
================================================================================

File Created:
  - Person.java

--------------------------------------------------------------------------------
A. WHAT HAS BEEN DONE
--------------------------------------------------------------------------------
We created a foundational class named `Person` to represent common human
attributes (id, name, email) that both library members and library staff share.

--------------------------------------------------------------------------------
B. THE CODE
--------------------------------------------------------------------------------

File: src/Person.java
--------------------
public class Person {

    private int id;
    private String name;
    private String email;

    public Person(int id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public int getId() {
        return id;
    }

    public void setId(int id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }

    @Override
    public String toString() {
        return "Person [id=" + id + ", name=" + name + ", email=" + email + "]";
    }
}

--------------------------------------------------------------------------------
C. CODE EXPLANATION
--------------------------------------------------------------------------------
- `private int id; private String name; private String email;`:
  Fields are marked `private`. This means outside classes cannot directly reach
  in and mutate `person.name = "Hacked";`.
- `public Person(int id, String name, String email)`:
  This is a parameterized constructor. It requires caller code to supply an ID,
  name, and email whenever a new Person object is instantiated.
- `this.id = id;`:
  The keyword `this` refers to the current object instance. It differentiates the
  instance variable `this.id` from the constructor argument `id` (variable
  shadowing).
- Getters & Setters (`getId`, `setId`, etc.):
  Public methods that provide controlled access to read and update private fields.
- `@Override public String toString()`:
  In Java, every class inherits from `java.lang.Object`. By default, calling
  `System.out.println(person)` prints an unreadable memory address like
  `Person@4f24324`. Overriding `toString()` prints a clean, human-readable
  representation of the person's data.

--------------------------------------------------------------------------------
D. CORE CONCEPTS USED
--------------------------------------------------------------------------------
1. Encapsulation: Grouping data (fields) and methods that operate on that data
   into a single unit (class), while hiding internal object state using `private`
   access modifiers.
2. Data Hiding: External classes can only access fields through getters and
   setters. This allows future validation (e.g., verifying an email format before
   setting it).
3. The DRY Principle (Don't Repeat Yourself): Instead of writing `id`, `name`,
   and `email` inside both `Member` and `Librarian`, we consolidate them in one
   place.
4. Polymorphic String Conversion (`toString`): Providing a custom string
   representation for debugging and logging.

--------------------------------------------------------------------------------
E. WHY WE DID THIS STEP
--------------------------------------------------------------------------------
In a library system, both borrowers and staff members have basic identity traits:
a unique identifier, a legal name, and contact details. Creating `Person` as a
parent class allows us to leverage inheritance in subsequent steps, keeping our
codebase clean, organized, and extensible.

4. STEP 3: DOMAIN MODELING FOR INVENTORY (BOOK)
================================================================================

File Created:
  - Book.java

--------------------------------------------------------------------------------
A. WHAT HAS BEEN DONE
--------------------------------------------------------------------------------
We modeled physical books in the library. Each book stores an ISBN, a title, an
author, and an availability status (`BookStatus`). When created, a book is
automatically marked as AVAILABLE.

--------------------------------------------------------------------------------
B. THE CODE
--------------------------------------------------------------------------------

File: src/Book.java
------------------
public class Book {

    private String isbn;
    private String title;
    private String author;
    private BookStatus status;

    public Book(String isbn, String title, String author) {
        this.isbn = isbn;
        this.title = title;
        this.author = author;
        this.status = BookStatus.AVAILABLE;
    }

    public String getIsbn() {
        return isbn;
    }

    public void setIsbn(String isbn) {
        this.isbn = isbn;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public String getAuthor() {
        return author;
    }

    public void setAuthor(String author) {
        this.author = author;
    }

    public BookStatus getStatus() {
        return status;
    }

    public void setStatus(BookStatus status) {
        this.status = status;
    }

    @Override
    public String toString() {
        return "Book [isbn=" + isbn + ", title=" + title + ", author=" + author + ", status=" + status + "]";
    }
}

--------------------------------------------------------------------------------
C. CODE EXPLANATION
--------------------------------------------------------------------------------
- `private BookStatus status;`:
  Here we use the `BookStatus` enum created in Step 1 as a field type. This is an
  example of object composition ("Book has-a BookStatus").
- `this.status = BookStatus.AVAILABLE;`:
  Inside the constructor, we automatically assign `BookStatus.AVAILABLE`. The
  caller only needs to supply `isbn`, `title`, and `author`.
- Comprehensive Getters/Setters:
  Allows reading and modifying each field while keeping all fields `private`.
- `toString()`:
  Prints full book details including its current availability status.

--------------------------------------------------------------------------------
D. CORE CONCEPTS USED
--------------------------------------------------------------------------------
1. Object Composition (Has-A Relationship): A Book is not an enum; it HAS a
   status of type `BookStatus`.
2. Default State Initialization: New books entering a library catalog are almost
   always available for borrowing immediately. Automatically setting
   `this.status = BookStatus.AVAILABLE` inside the constructor removes the
   burden of passing `BookStatus.AVAILABLE` every time a new book is added.
3. Domain Identity (ISBN): In publishing and libraries, the ISBN (International
   Standard Book Number) uniquely identifies a specific title and edition.

--------------------------------------------------------------------------------
E. PITFALL AVOIDED & DESIGN EVOLUTION
--------------------------------------------------------------------------------
- In our initial draft, `status` had package-private visibility (`BookStatus status;`),
  while `isbn`, `title`, and `author` were `private`.
  We refactored it to `private BookStatus status;` to ensure strict, consistent
  encapsulation across all fields.
- Initially, the constructor required passing the status manually:
  `Book(isbn, title, author, status)`. We simplified it so new books default
  sensibly to `BookStatus.AVAILABLE`.

--------------------------------------------------------------------------------
F. WHY WE DID THIS STEP
--------------------------------------------------------------------------------
Books are the primary inventory asset of a library. The entire library system
revolves around tracking books, searching for them, issuing them, and accepting
returns. Encapsulating metadata (title, author, ISBN) with real-time state
(AVAILABLE/BORROWED) is essential for any borrowing transaction.

5. STEP 4: ESTABLISHING ROLE SPECIALIZATION VIA INHERITANCE (LIBRARIAN & MEMBER)
================================================================================

Files Created:
  - Librarian.java
  - Member.java (initial structure)

--------------------------------------------------------------------------------
A. WHAT HAS BEEN DONE
--------------------------------------------------------------------------------
We created two specialized classes that inherit from `Person`:
1. `Librarian`: Represents library staff who manage the catalog and operations.
2. `Member`: Represents library patrons who check out books.

--------------------------------------------------------------------------------
B. THE CODE
--------------------------------------------------------------------------------

File: src/Librarian.java
-----------------------
public class Librarian extends Person {

    public Librarian(int id, String name, String email) {
        super(id, name, email);
    }
}

--------------------------------------------------------------------------------
C. CODE EXPLANATION
--------------------------------------------------------------------------------
- `public class Librarian extends Person`:
  The `extends` keyword tells Java that `Librarian` inherits all public and
  protected properties and methods of `Person`.
- `super(id, name, email);`:
  The keyword `super` refers to the superclass (parent class), which is `Person`.
  Because `Person` has a parameterized constructor, the child class constructor
  MUST invoke `super(...)` to initialize the parent's `id`, `name`, and `email`.

--------------------------------------------------------------------------------
D. CORE CONCEPTS USED
--------------------------------------------------------------------------------
1. Inheritance (IS-A Relationship): A `Librarian` IS-A `Person`. A `Member` IS-A
   `Person`. All methods defined on `Person` (`getId()`, `getName()`, `setEmail()`)
   are automatically available on `Librarian` and `Member` without writing them again.
2. Constructor Chaining / Delegation: In Java, a child constructor cannot run
   without first running a parent constructor. Calling `super(id, name, email)`
   delegates initialization to the parent class safely.
3. Code Reusability: We wrote identity logic once in `Person` and reused it across
   multiple distinct roles.

--------------------------------------------------------------------------------
E. WHY WE DID THIS STEP
--------------------------------------------------------------------------------
In a library, members and librarians have very different responsibilities:
- Members have accounts, borrow limits, and lists of checked-out books.
- Librarians have staff privileges, issue books, and manage the system.
If we had put everything into one monolithic class, we would violate the Single
Responsibility Principle. Inheritance lets us share common attributes while
giving each role its own room to grow specialized behavior.

6. STEP 5: ADVANCED MEMBER STATE, ENUM BINDING & COLLECTIONS
================================================================================

File Updated:
  - Member.java

--------------------------------------------------------------------------------
A. WHAT HAS BEEN DONE
--------------------------------------------------------------------------------
We expanded `Member` from an empty subclass into a rich domain model:
1. Bound the `AccountStatus` enum to track whether a member's account is ACTIVE
   or CLOSED.
2. Integrated a `List<Book>` to dynamically store the books currently checked out
   by the member.
3. Initialized the collection inside the constructor to guarantee null-safety.
4. Added getters, setters, and an overridden `toString()` method.

--------------------------------------------------------------------------------
B. THE CODE
--------------------------------------------------------------------------------

File: src/Member.java
--------------------
import java.util.ArrayList;
import java.util.List;

public class Member extends Person {

    private AccountStatus status;
    private List<Book> borrowedBooks;

    public Member(int id, String name, String email) {
        super(id, name, email);
        this.status = AccountStatus.ACTIVE;
        this.borrowedBooks = new ArrayList<>();
    }

    public AccountStatus getStatus() {
        return status;
    }

    public void setStatus(AccountStatus status) {
        this.status = status;
    }

    public List<Book> getBorrowedBooks() {
        return borrowedBooks;
    }

    public void setBorrowedBooks(List<Book> borrowedBooks) {
        this.borrowedBooks = borrowedBooks;
    }

    @Override
    public String toString() {
        return "Member [status=" + status + ", borrowedBooks=" + borrowedBooks + "]";
    }
}

--------------------------------------------------------------------------------
C. CODE EXPLANATION
--------------------------------------------------------------------------------
- `import java.util.ArrayList; import java.util.List;`:
  Imports standard Java Collections Framework utilities.
- `private List<Book> borrowedBooks;`:
  Declares an ordered collection of `Book` references. Notice the type is the
  interface `List`, not the concrete class `ArrayList`.
- `this.status = AccountStatus.ACTIVE;`:
  When a member is registered, their account is initialized to `ACTIVE` by default.
- `this.borrowedBooks = new ArrayList<>();`:
  CRITICAL: Instantiates an empty `ArrayList` in memory and assigns it to
  `borrowedBooks`.
- `@Override public String toString()`:
  Prints the member's account status and current list of borrowed books.

--------------------------------------------------------------------------------
D. CORE CONCEPTS USED
--------------------------------------------------------------------------------
1. Programming to an Interface (`List` vs. `ArrayList`):
   We declare `private List<Book> borrowedBooks;` instead of
   `private ArrayList<Book> borrowedBooks;`.
   In Java, `List` is an interface and `ArrayList` is a concrete implementation.
   Programming to the interface decouples our class from the specific list
   implementation, allowing us to change to a `LinkedList` or another list type
   later without breaking other parts of the application.
2. Defensive Programming & Null-Safety:
   If we did NOT write `this.borrowedBooks = new ArrayList<>();`, the field
   `borrowedBooks` would default to `null`.
   Later, when a member attempts to borrow a book:
     `member.getBorrowedBooks().add(book);`
   Java would attempt to call `.add()` on `null`, triggering a runtime
   `NullPointerException` (NPE) and crashing the application!
   Initializing to an empty list guarantees the object starts in a valid state.
3. 1-to-Many Aggregation:
   A single `Member` can hold zero, one, or many `Book` instances.

--------------------------------------------------------------------------------
E. WHY WE DID THIS STEP
--------------------------------------------------------------------------------
A member exists to borrow books. Connecting `AccountStatus` ensures that the
system can check if an account is in good standing before lending books, and
holding a `List<Book>` gives the member their own personalized inventory tracking.

A. WHAT HAS BEEN DONE

We maintained the standard Java entry point class `App.java`.

public class App {

        System.out.println("Hey there, Welcome to Offline Wikipedia!");

--------------------------------------------------------------------------------
C. CODE EXPLANATION
--------------------------------------------------------------------------------
- `public static void main(String[] args)`:
  The standard signature required by the Java Virtual Machine (JVM) to execute
  any Java application.
  - `public`: Accessible to the JVM from anywhere.
  - `static`: Can be invoked without creating an instance of `App`.

--------------------------------------------------------------------------------
D. WHY WE DID THIS STEP
--------------------------------------------------------------------------------
This serves as the executable harness where we can wire our classes together,
instantiate members, create books, simulate checkout transactions, and test our
business logic in the console.

       `public void borrowBook(Book book)`
